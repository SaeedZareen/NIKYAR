# معماری نیک‌یار (نسخه‌ی ۲)

## اصل اصلی: «هسته + ماژول»

```
┌──────────────────────── فرانت‌اند (React + TypeScript + Tailwind v4 + وایب‌فارسی) ────────────────────────┐
│  app/        پوسته، احراز هویت، رجیستری ماژول‌های فرانت                                                 │
│  core/       فرم‌ساز، فرایندساز، کارتابل، فهرست‌های پایه، سازمان، نقش‌ها، سوابق                          │
│  modules/    پرونده‌ی پرسنلی و ماژول‌های آینده                                                          │
└────────────────────────────────────────────── REST API (/api) ───────────────────────────────────────────┘
┌──────────────────────────────────────────── بک‌اند (Django + DRF) ──────────────────────────────────────┐
│  core/kernel         رجیستری ماژول‌ها (ModuleSpec)، لایسنس، خطاهای فارسی، اعتبارسنجی ایرانی            │
│  core/accounts       کاربران، نقش‌ها، مجوزها (RBAC)، قفل حساب                                            │
│  core/org            واحدهای درختی، سمت‌ها، موتور انتساب کار                                             │
│  core/lookups        فهرست‌های پایه: «سیستمی» (قفل) و «قابل‌ویرایش»                                     │
│  core/forms          موتور فرم‌ساز: ۲۵ نوع فیلد، نسخه‌بندی، اعتبارسنجی سمت سرور                          │
│  core/workflow       موتور BPMN (SpiffWorkflow)، کارتابل، اقدام‌های سیستمی                               │
│  core/audit · files · numbering · notifications    سرویس‌های مشترک                                       │
│  modules/personnel   پرونده‌ی پرسنلی                                                                    │
└──────────────────────────────────────────────── PostgreSQL ─────────────────────────────────────────────┘
```

**قانون طلایی:** هسته هیچ‌وقت به ماژول‌ها وابسته نیست. ماژول‌ها فقط از هسته استفاده می‌کنند.

## یک ماژول چه چیزهایی به سامانه اضافه می‌کند؟

هر ماژول در `apps.py` یک `ModuleSpec` با نام `nikyar_module` اعلام می‌کند:

| بخش | مثال در ماژول پرسنلی | کجا ظاهر می‌شود |
|---|---|---|
| `permissions` | `personnel.employee.edit` | صفحه‌ی «نقش‌ها و دسترسی‌ها» |
| `lookups` | جنسیت (سیستمی)، بانک (قابل‌ویرایش) | «فهرست‌های پایه» و فرم‌ساز |
| `actions` | «ساخت پرونده‌ی پرسنلی» | فرایندساز ← «اقدام سیستمی» |
| `entities` | `personnel.employee` | فرم‌ساز ← «فیلد سفارشی» (low-code) |
| `sequences` | کد پرسنلی | شماره‌گذاری خودکار |

در فرانت‌اند، هر ماژول در `module.tsx` منو و مسیرهای خودش را اعلام می‌کند.
منو بر اساس **مجوز کاربر** و **لایسنس** خودکار فیلتر می‌شود.

## فهرست‌های پایه: سیستمی در برابر قابل‌ویرایش

| | سیستمی 🔒 | قابل‌ویرایش |
|---|---|---|
| منبع مقادیر | کد ماژول (همگام با هر migrate) | مدیر سامانه |
| افزودن/حذف/ویرایش | ممنوع | آزاد |
| چرا؟ | منطق برنامه به «کد» مقدار وابسته است | فقط برای انتخاب و گزارش است |
| مثال | وضعیت تأهل ← فقط «متأهل» می‌تواند همسر ثبت کند | بانک، رشته‌ی تحصیلی |

مقداری که در اطلاعات ثبت‌شده استفاده شده، حذف نمی‌شود؛ فقط غیرفعال می‌شود.

## فرم‌ساز و فرایندساز چطور با هم کار می‌کنند

1. در **فرم‌ساز** فرم فرایند را می‌سازید (مثلاً «فرم درخواست مرخصی») و منتشر می‌کنید.
2. در **فرایندساز** آن فرم را به‌عنوان «فرم اصلی» انتخاب می‌کنید.
3. برای هر مرحله تعیین می‌کنید هر فیلد **قابل‌ویرایش / فقط‌نمایش / مخفی** باشد.
4. برای هر مرحله **دکمه‌های اقدام** (تأیید/رد/بازگشت) تعریف می‌کنید؛ نتیجه در شرط مسیرها استفاده می‌شود.
5. با **اقدام سیستمی** یک مرحله می‌تواند کاری در ماژول‌ها انجام دهد (مثل ساخت پرونده‌ی پرسنلی).

سرور هر ورودی را دوباره اعتبارسنجی می‌کند و فیلدهایی که در آن مرحله قابل‌ویرایش نیستند را نمی‌پذیرد.

## نسخه‌بندی

فرم‌ها و فرایندها «پیش‌نویس» و «نسخه‌ی منتشرشده» دارند. هر درخواست با نسخه‌ای که با آن شروع شده
تا پایان ادامه می‌دهد؛ پس تغییر فرایند، درخواست‌های در جریان را خراب نمی‌کند.

## رابط کاربری

- همه‌ی کامپوننت‌ها از **وایب‌فارسی** (`src/components/ui`) هستند؛ چرخ از نو ساخته نمی‌شود.
- قوانین طراحی در `AGENTS.md` (راست‌چین، اعداد فارسی، تاریخ شمسی، توکن‌های رنگ).
- دو تم: «گرافیت» (تیره) و «کاغذ» (روشن)؛ هر کاربر خودش انتخاب می‌کند.
- سرور MCP وایب‌فارسی در `.mcp.json` تنظیم شده است.
